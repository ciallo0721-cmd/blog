# 架构评审意见

> 日期: 2026-03-25 | 评审人: 程基岩 (工程负责人)
>
> 评审框架: PASS / CONCERNS / FAIL

---

## 总体判定: **CONCERNS** (有条件通过)

当前架构**可以**支持新增功能和内容，但需要在开始大规模开发前完成若干基础重构。架构本身在技术选型和设计模式上都是合理的，主要风险在代码组织层面。

---

## 逐项评审

### 1. 技术栈选择: **PASS** ✅

| 评审项 | 结果 | 说明 |
|--------|------|------|
| Vanilla JS | ✅ PASS | 对于 GitHub Pages 纯静态 ARG 是正确的选择 |
| 零依赖 | ✅ PASS | 部署简单，长期稳定，不随框架版本迁移 |
| CSS3 无预处理器 | ✅ PASS | 236 行 CSS 不需要 Sass/Less |
| HTML5 单页面 | ✅ PASS | 所有内容一页呈现，符合 ARG 沉浸式体验 |
| 无模块系统 | ✅ PASS | 当前规模下合理，但接近需要引入模块化的临界点 |

**结论**: 技术栈在给定约束下是最优解。不需要改变。

### 2. 架构设计: **PASS** ✅

| 评审项 | 结果 | 说明 |
|--------|------|------|
| 状态管理 (GAME_STATE) | ✅ PASS | 单一状态源，结构清晰，字段命名合理 |
| 状态机驱动渲染 | ✅ PASS | `browserPhase` 和 `terminalPhase` 状态机设计正确 |
| 数据与逻辑分离 | ✅ PASS | FORUM_POSTS/ENDINGS 与渲染逻辑在概念上分离 |
| 模块边界 | ✅ PASS | 窗口管理、浏览器渲染、终端交互各自独立 |
| 结局系统 | ✅ PASS | triggerEnding → 终端展示 → overlay 的分层设计好 |

**结论**: 架构骨架坚实，适合扩展。状态机设计是最大的架构亮点。

### 3. 代码组织: **CONCERNS** ⚠️

| 评审项 | 结果 | 说明 |
|--------|------|------|
| 单文件大小 | ⚠️ CONCERNS | 720 行 / 33KB，接近维护阈值 |
| HTML-in-JS | ⚠️ CONCERNS | 大量内嵌 HTML 字符串降低可维护性 |
| 命令处理 | ⚠️ CONCERNS | 130 行 switch 语句需要注册表模式 |
| 全局命名空间 | ⚠️ CONCERNS | 100+ 个同级 JS 文件存在冲突风险 |
| 文件目录结构 | ⚠️ CONCERNS | 游戏文件散落在共享目录中，无独立命名空间 |

**结论**: 代码组织是当前架构的主要薄弱点。建议在新功能开发前完成 ADR-004 的文件拆分。

### 4. 可测试性: **CONCERNS** ⚠️

| 评审项 | 结果 | 说明 |
|--------|------|------|
| 单元测试 | ❌ 缺失 | 无任何测试基础设施 |
| 状态机测试 | ❌ 缺失 | 状态转换未经自动化验证 |
| 命令解析测试 | ❌ 缺失 | 终端命令未经自动化验证 |
| 手动测试路径 | ✅ 存在 | 4 个结局路径可手动走通 |

**结论**: 当前所有测试依赖手动回归，效率低且易遗漏。建议搭建最小测试框架。

### 5. 安全性: **PASS** ✅

| 评审项 | 结果 | 说明 |
|--------|------|------|
| XSS | ✅ PASS | 纯静态，无用户生成内容注入 |
| 数据暴露 | ✅ PASS | 所有数据为公开叙事内容 |
| 服务端安全 | ✅ N/A | 无服务端 |
| 第三方脚本 | ✅ PASS | 仅 GA4 分析（可接受） |

**结论**: 纯静态 ARG 的安全攻击面极小，无需特别关注。

### 6. 性能: **PASS** ✅

| 评审项 | 结果 | 说明 |
|--------|------|------|
| 初始加载 | ✅ PASS | ~33KB JS + ~12KB CSS + 极小 HTML |
| 运行时性能 | ✅ PASS | 720 行 JS 在 2026 年浏览器上瞬间执行 |
| 内存 | ✅ PASS | 无内存泄漏风险（无定时器泄漏、无闭包泄漏） |
| DOM 操作 | ✅ PASS | 当前规模下 innerHTML 全量重建不是瓶颈 |

**结论**: 性能不是当前阶段的关注点。仅在终端历史 > 100 条或新增大量动画时需要注意。

## 对新功能开发的评估

### 可以安全添加的功能（无需重构）

1. **新增论坛帖子**: 向 `FORUM_POSTS` 数组添加条目即可
2. **新增结局**: 向 `ENDINGS` 对象添加键值对，在 `terminalKeydown` 的 switch 中添加触发命令
3. **新增终端命令**: 在 `terminalKeydown` 的 switch 中添加 case
4. **修改叙事文本**: 直接编辑 JS 中的字符串
5. **调整样式**: 修改 CSS 文件，无需动 JS

### 需要轻度重构才能安全添加的功能

1. **新增窗口类型**（如文件管理器）: 需要扩展 `windows` 对象和窗口管理逻辑
2. **浏览器历史导航**: 需要实现 `browserBack()`/`browserFwd()` 的栈逻辑
3. **存档/读档系统**: 需要实现 GAME_STATE 序列化到 localStorage

### 不应在重构前添加的功能

1. **复杂的新终端交互**（如分支对话树）: 130 行 switch 已经难以维护
2. **新游戏阶段**（如论坛之前的"桌面探索"）: 需要更复杂的状态机
3. **多语言支持**: 当前 HTML-in-JS 模式对 i18n 极不友好

## 重构路线图建议

```
阶段 0 (1-2 天) — 基础卫生
  ├── 创建 GAME_STATE schema 文档
  ├── 用 IIFE 包裹代码，减少全局污染
  └── 修复已知 bug（minWindow/closeWindow 区分、maxWindow 还原）

阶段 1 (2-3 天) — 文件拆分 [阻塞新功能]
  ├── 拆分为 data / state / window / browser / terminal / ending 6 个文件
  ├── 更新 index.html 的 <script> 加载顺序
  └── 手动回归测试全部 4 个结局

阶段 2 (1-2 天) — 代码质量
  ├── 终端命令重构为注册表模式
  ├── 提取 HTML 模板
  └── 添加基础测试

阶段 3 — 开始新功能开发
  └── 在干净的代码基础上开发新功能
```

## 风险矩阵

| 风险 | 概率 | 影响 | 缓解措施 |
|------|------|------|----------|
| 单文件膨胀导致维护困难 | 高 | 中 | ADR-004 拆分计划 |
| 全局命名冲突 | 低 | 高 | IIFE 包裹 |
| 缺少测试导致回归 bug | 中 | 中 | 搭建测试框架 |
| 新功能与现有状态机冲突 | 低 | 中 | GAME_STATE schema 文档化 |
| GitHub Pages 部署失败 | 极低 | 高 | 零构建步骤，天然免疫 |

---

## 最终建议

「镜中人」的架构在核心设计（状态机、数据分离、零依赖）上是优秀的，需要改进的是代码组织层面。

**建议在开始新功能开发前，投入约 5 个工作日完成阶段 0 + 阶段 1（文件拆分 + 基础卫生），这将在后续开发中节省远超 5 天的时间。**

如果时间紧迫必须立即开始新功能，至少要完成：
1. GAME_STATE schema 文档（1 小时）
2. IIFE 包裹 + 命名空间（2 小时）
3. 写清楚每个新功能在哪段代码附近添加（30 分钟）
