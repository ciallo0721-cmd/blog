# ADR-002: 论坛帖子数据内联在 JavaScript 中而非从外部 JSON 加载

- **状态**: 已采纳 (Accepted)
- **日期**: 2026-03-25（文档化日期；决策最初于项目启动时做出）
- **决策者**: 项目作者
- **ADR 编号**: 002

---

## 上下文

「镜中人」核心内容是 12 条论坛帖子和 4 个结局文本。这些是游戏的叙事内容（约 4KB 文本），需要被浏览器渲染。

数据加载方式有两种：内联在 JS 中 vs 从外部 JSON 文件 fetch。

---

## 决定

**将 `FORUM_POSTS` 数组和 `ENDINGS` 对象直接内联在 `arg-index.js` 中。**

---

## 备选方案

### 方案 A: 外部 JSON 文件（已否决）

**优点:**
- 数据与逻辑分离，便于非程序员编辑内容
- 可按需延迟加载

**否决理由:**
- 需要额外的 HTTP 请求（fetch XHR），对 GitHub Pages 静态托管无实质好处
- 数据量极小（~4KB），内联不造成显著的加载性能问题
- JSON 文件需要异步加载，增加初始化复杂度（需要 loading 状态、错误处理）
- JSON 不支持注释、模板字面量和函数引用；内联 JS 对象更灵活
- 项目当前由开发者直接编辑，不需要面向非技术人员的编辑界面

### 方案 B: HTML 内嵌 `<script type="application/json">`（已否决）

**优点:**
- 数据在 HTML 中可见，无需额外 JS 文件

**否决理由:**
- 增加 HTML 文件复杂度
- 没有解决任何实际问题（仍然需要 JS 解析）

---

## 后果

### 正面

1. **零网络延迟**: 数据随 JS 文件一次性加载，页面初始化无需等待额外请求
2. **同步可用**: 所有渲染函数可以同步访问数据，无需 async/await 或 Promise
3. **灵活**: 可以内联 HTML 片段、使用模板字面量中的变量
4. **简单**: 不需要 fetch 错误处理、重试逻辑、或加载状态 UI

### 负面

1. **内容编辑耦合**: 修改文本需要编辑 JS 文件，对于非开发人员不够友好
2. **JS 文件体积**: 数据增加 JS 文件约 4KB（占总文件 ~12%）
3. **缺少结构化验证**: 没有 JSON Schema 来验证数据格式
4. **国际化困难**: 如需多语言支持，数据与代码的耦合会导致重复

### 缓解措施

- 使用清晰的数据结构注释和分区（`/* FORUM POSTS 数据 */`、`/* 结局数据 */`）
- 保持数据对象的扁平化和可读性
- 当内容编辑频率增加时，考虑将数据抽取到 `data/` 目录下的独立 JS 文件（仍为静态引入，非 fetch）

---

## 未来演进路径

如果团队中出现非技术内容编辑者，或数据量增长到 >100KB，可迁移到：

```
arg/
├── data/
│   ├── forum-posts.js    ← FORUM_POSTS 变量导出
│   └── endings.js        ← ENDINGS 变量导出
├── js/
│   └── game-logic.js     ← 业务逻辑
└── index.html            ← 按顺序加载 data/*.js 再加载 game-logic.js
```

这样数据文件可以被非开发人员独立编辑，且仍然保持静态加载（无 fetch 延迟）。

## 合规验证

- [x] 无 `fetch()` 调用加载游戏数据
- [x] 无 `<script type="application/json">` 标签
- [x] `FORUM_POSTS` 和 `ENDINGS` 在 JS 文件顶部定义，紧接 `GAME_STATE`
